# KC: язык, формат объекта и как компилировал Egosoft

Игровая логика X3: Terran Conflict и Albion Prelude написана на внутреннем языке Egosoft — KC — и скомпилирована
в объектные файлы `STOR`: `L/x3story.obj`, `L/x3intro.obj`, `L/x3galedit.obj`, `L/x3config.obj`. Всё ниже
выведено из байткода и проверено полным кругом: объект → исходник → объект даёт тот же файл байт в байт для
каждого объекта каждой версии TC и AP.

## Язык исходников
Синтаксис Си-подобный, значения динамические: int, double, строка, массив, таблица, объект.

**Файл исходника** (`x3story.kc`) — последовательность объявлений в порядке кода:
- директивы: `#object <версия> <build>`, `#sections …` (порядок секций), `#pool`, `#patch`, `#stamp` (метка build
  полей и классов по умолчанию);
- `var gN = …;` — глобальные переменные (поля класса 0, секция VARS);
- `function F(arg1, …) { … }` — глобальные функции (секция SYMB);
- `class C150 : C100 { var m5 = 0; … function Init(arg1) { … } }` — классы (CLAS). Номер поля — его позиция:
  собственные поля нумеруются после полей родителей. Имя `mN` по умолчанию — абсолютный номер поля. Любой класс
  можно назвать: `class Client = 150 : C100`.
- Инициализаторы полей: число, `"строка"`, `{}` (массив), `{:}` (таблица), без значения (пусто) или
  `__init(тип, значение)`. Например, `__init(2, 0)` — строка со смещением 0 в пуле; VM читает её как
  `"SB_String(0)"`, а не как `""`.
- `@0x…` после класса или поля — метка сборки, в которой он появился (см. «Моды и сейвы»).

**Переменные.** Параметры — `arg1…`, локальные — `v1…`, поля — `mN`, глобальные — `gN` (пока их не назовут
аннотации). Локальная живёт до конца своего блока `{ }`; каждая секция `case` — блок.

**Выражения** (приоритет как в Си): `= += -= …`, `?:`, `||`, `&&`, `|`, `^`, `&`, `== !=`, `< > <= >=`,
`<< >>`, `+ -`, `* / %`, унарные `! - ~ new delete`, `++`/`--`, `a[i]`, вызовы.
- `&&` и `||` всегда дают 0 или 1.
- Деление на 0 даёт 0.
- `+` со строкой склеивает строки.
- Литералы: `{a, b}` — массив (элемент 0 первый), `{k: v, …}` — таблица. Целые 32-битные: `0xFFFFFFFF` — это -1,
  числа больше — ошибка.
- Значение присваивания — новое значение.

**Вызовы** (вид записи определяет опкод):

| Запись | Опкод | Смысл |
|---|---|---|
| `F(a)` | `calls` / `callg` / `native` | метод своего класса или предков (статически); иначе глобальная функция; иначе натив |
| `::F(a)` | `callg` | глобальная функция явно |
| `C1000::F(a)` | `calls` | метод указанного класса на текущем объекте (как `Base::f()` в C++) |
| `this->F(a)` | `calln` | виртуальный вызов по имени на текущем объекте |
| `x.F(a)` | `callo` | вызов по имени на объекте `x` (id или ссылка), разрешается во время выполнения |
| `C150.F(a)` | `callc` | статический вызов метода класса 150 на объекте-классе 150 («синглтоны») |
| `x.C150::F(a)` | `callc` | статический вызов C150::F на объекте `x` |
| `new C661(a)` | `new` + `callo Create` | создать объект и вызвать `Create(a)` |
| `native::SE_X(a)` | `native` | натив, чьё имя перекрыто методом |

Вызовы по имени (`callo`, `calln`) дополняют недостающие аргументы нулями.

**Операторы:** `var`, `if/else`, `while`, `for (init; cond; step)`, `do … while`, `switch`, `return [e]`,
`break`, `continue`, `fork { … }`, блоки.
- `fork { … }` запускает тело в дочерней задаче с копией кадра, родитель идёт дальше. `break` и `continue` не могут
  выйти из тела `fork`.
- `switch` принимает целые и строковые `case`. Плотная таблица (опкод 0x78) выбирается, когда диапазон значений не
  больше 20 × число case, иначе 0x79. `: dense`, `: sparse` и `: dense(lo, hi)` задают таблицу явно. Повтор case —
  ошибка.

**Запасная форма** — `function F(arg1) frame N asm { … }` с метками `L0012:` и мнемониками из `kcisa.py`.
`x3kc decompile --asm-all` пишет так все методы. Для стоковых объектов она ни разу не понадобилась.

## Как компилировал Egosoft
- **Кадр при входе**, снизу вверх: `argN … arg1, argc, адрес возврата, контекст`. `ldl n` / `stl n` считают от
  вершины (n = 1 — вершина), поэтому номер локальной зависит от глубины стека.
- **Локальная** — значение, оставленное на стеке: `var x = e;` → `e`, `var x;` → `push0`. Конец блока: `pop` или
  `popn n`.
- **Вызов:** аргументы с последнего, затем `argc` константой, затем (для `callo`/`callc`) объект. Элементы
  массива и пары таблицы — тоже с последнего; в паре сначала значение, потом ключ.
- **Логика и ветвления:**
  - `a && b`: `a jf F; b jf F; push1; jmp E; F: push0; E:`; `||` — то же с `jt` и обратными константами;
  - `c ? a : b`: `c jf F; a; jmp E; F: b; E:`;
  - `if`: `c jf L1; then; [jmp L2; L1: else]; L2:`.
- **Циклы:** `while`: `S: c jf X; тело; jmp S; X:`; `for`: `init; S: c jf X; jmp B; I: step; jmp S; B: тело;
  jmp I; X:`; `do`: `S: тело; c; jt S`.
- **`switch`:** `e; jmp D; секции; jmp End; D: таблица; End:` — таблица стоит после тел.
- **`fork`:** `fork; jt L; тело; exit; L:`.
- **Возвраты:** `return e`: `e; stl k+1; pop/popn k; ret` (k — живые локальные); `return;`: `pop/popn k; push0;
  ret`; функция: `frame N; тело; снятие локальных; push0; ret`. Мёртвый код после `return` не убирался.
- **`frame N`** — максимальная глубина стека над кадром: эпилог `push0; ret` и `push0` в `return;` не считаются;
  `calls`/`calln` на миг считают лишнюю ячейку, `callg`, `callo`, `callc` и нативы — нет. Правило верно для всех
  методов всех объектов; поле «locals» строки метода равно ему.
- **Константы** — всегда в самой короткой форме: `push0..3`, `pushb`, `pushw`, `pushd`; `neg` от литералов нет.

## Формат объекта (`STOR`)
- Заголовок `STOR`, версия, build; секции `CODE`, `SYMB`, `VARS`, `CLAS`, `STRG` (или `STRU`), иногда `PTCH`;
  в конце `/STO`.
- **Строка метода (16 байт):** смещение кода, имя (смещение в пуле), frame, число параметров.
- **Строка поля:** номер (позиция в своём классе), значение, тип, метка build. Типы: 0 — пусто, 1 — int,
  2 — строка (значение — смещение в пуле), 8 — массив, 9 — таблица.
- **Запись класса:** id, родитель, метка build, методы, поля. Имён классов, полей и локальных в объекте **нет**,
  есть только имена методов.
- **Порядок:** методы класса лежат в коде подряд, в порядке строк; порядок классов в CLAS совпадает с кодом;
  глобальные функции идут кусками между классами (границы исходных файлов).
- **STRG** — пул строк, только дописывается: сейвы хранят смещения строк, поэтому в пуле живут строки старых
  версий, которые код уже не использует. Компилятор берёт пул из `.pool` и дописывает новые строки. `""` в коде —
  вторая пустая строка пула, никогда не смещение 0.
- **PTCH** — карты адресов для сейвов старых сборок: записи «build, число пар, пары `(old, new)`».

## Моды и сейвы (`x3kc compile --base`)
Как это работает в игре (`Script::LoadVmState`, X3AP.exe 0x004a0880):
- сейв хранит build объекта;
- если build другой, берётся запись PTCH для build сейва; без неё **сейв не загрузится**;
- запись — кусочный сдвиг: для pc берётся последняя пара с `old ≤ pc`, и pc становится `pc + (new − old)`;
  `new = 0` — «кода нет»; pc ниже первой пары не меняются;
- так пересчитываются pc каждой задачи и все адреса возврата на её стеке;
- поле, чья метка новее build сейва, из сейва не читается и получает начальное значение.

Что делает `compile --base база.obj`:
1. Даёт объекту новый build: текущее время, но больше всех известных базе. Задать можно через `--build` или
   `#object`; build базы и build, для которых у базы уже есть записи PTCH, не принимаются.
2. Ставит новый build меткой добавленным полям, глобальным и классам, если метка не задана в исходнике.
3. Строит карту «адреса базы → новые»: методы по имени, инструкции внутри метода выравниваются `difflib`.
   Сохранённый pc — всегда адрес после инструкции, поэтому он едет вместе с инструкцией перед ним; если та
   изменена, адрес считается удалённым.
4. Пересобирает каждую запись PTCH **базы** через эту карту и добавляет запись для build базы. Так мод можно
   собирать поверх своей прошлой версии (`--base mod_v1.obj`), и загружаются и стоковые сейвы, и сейвы v1.
5. Проверяет, что каждый адрес возврата базы попал после того же вызова (тот же натив, тот же метод) внутри метода
   с тем же размером кадра: лишняя локальная сдвинула бы все локальные приостановленного вызова. Адресом возврата в
   сейве может быть только вызов, в котором задача способна приостановиться: натив, который может ждать, и метод,
   который до такого натива доходит, транзитивно (вызов по имени считается, если может хоть один метод с этим
   именем). Какие нативы всегда отвечают сразу, записано в `x3kc/sync_natives.txt`: анализ потока диспетчеров
   нативов в X3AP.exe для групп B3D, INS, SA, X2 и SE (на каждом пути обработчик возобновляет задачу до возврата
   из диспетчера) плюс спецификации обработчиков SE/TI. Нативы остальных групп считаются возможно ждущими. Поэтому
   изменение кадра в методе, который только рисует или считает (B3D, SE, большинство SA), сборку не останавливает,
   а в методе, который ждёт (TI_Delay, команды полёта, команды MSCI), — останавливает.
6. Если что-то ломает сейвы — потерянные поля, удалённый класс, сменившийся родитель, неверные адреса возврата, —
   ничего не пишется, код выхода 3; `--force` пишет всё равно.

Правила для мода: поля добавлять **только в конец** класса; поля не удалять и не переставлять; новые начальные
значения до старых сейвов не дойдут (компилятор предупреждает).

**В игре не проверено:** загрузка пересобранного объекта и загрузка старого сейва с ним. Подпись x3story из
`x3files.xml` к изменённому файлу не подойдёт, игра пометит себя как «modified».

## Аннотации
Кроме имён методов, в объекте имён нет, поэтому `x3kc decompile` печатает `C150`, `m12`, `v3`, `arg1`. Имена и
комментарии хранятся вне исходника, в JSON, и применяются при каждой декомпиляции:

```
x3kc decompile x3story.obj src --names auto           встроенные имена (x3kc/data)
x3kc decompile x3story.obj src --names mine.json      свои
```

Имена не меняют байты: исходник с именами собирается в тот же объект. Имена, которые не разрешились бы обратно
(ключевые слова, дубли, затенение), получают суффикс, и каждая такая правка печатается строкой `names:`.

**Две формы:**
- *Рабочая* — комментарии по адресу кода, как их печатает `x3kc decompile --pcs` (`// @0012fb`). Её пишут при
  разметке; она подходит только к одной сборке.
  ```
  {"classes": {"150": {"name": "Client", "doc": "…",
                       "fields": {"3": {"name": "fastForward", "doc": "…"}},
                       "methods": {"Init": {"doc": "…", "params": ["sectorName"], "locals": {"v1": "ship"},
                                            "comments": {"0x012fb3": "…"}}}}},
   "globals": {"fields": {"33": {"name": "gPatchTable"}}, "methods": {…}}}
  ```
  Ключ поля — номер среди собственных полей класса (0 — первое своё поле).
- *Переносимая* (`x3kc names pack <obj> <рабочая.json> <out.json>`) — добавляет раскладку полей каждого класса,
  хеш тела каждого метода и окно хешей инструкций вокруг каждого комментария. `decompile` применяет её к любой
  сборке: имена полей — пока совпадает раскладка, параметры — при том же числе, локальные — при том же теле,
  комментарии находятся заново по окну. `x3kc names unpack` возвращает рабочую форму для нужной сборки.

Встроенные имена сделаны для AP 3.3 (build 1510658513) LLM-агентами по коду, текстам игры и именам dobj из
X3_Customizer. Человеком они не вычитаны; документацию со словом «probably» считайте догадкой. На AP 1.0 из них
применяются 1 698 имён полей и 6 583 из 6 667 комментариев.
