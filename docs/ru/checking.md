# Проверка мода без игры

Перебрать всю функциональность в игре — многие часы, поэтому x3kc проверяет всё, что можно, до её запуска:
статический верификатор байткода и эмулятор скриптовой VM игры, который исполняет код самого объекта.

## Статические проверки
- `x3kc verify obj [-v]` — верификатор байткода. `x3kc compile` запускает его после каждой сборки и при ошибке
  ничего не пишет (код выхода 4; `--force` пишет всё равно). На каждом пути исполнения каждого метода
  проверяется:
  - `frame N` совпадает со строкой метода, стек не выходит за N + 4 ячейки, которые резервирует VM, глубина
    одинакова на всех путях в инструкцию и не опускается ниже кадра, `ret` оставляет ровно одно значение;
  - переходы и метки `switch` ведут на начало инструкции внутри метода, неизвестных опкодов нет, исполнение
    не проваливается за конец метода;
  - локальные не выходят за кадр, записи не задевают ячейки argc / адреса возврата / контекста;
  - поля и глобальные существуют, прямые вызовы идут на входы методов с верным числом аргументов, `argc`
    каждого вызова — известная константа;
  - (предупреждения) имена вызовов по имени и нативов существуют; отсутствие — не падение, VM отвечает 0.

  - для объекта целиком: каждый класс в CLAS идёт после своего родителя, родителя 0 нет, id классов не
    повторяются. Загрузчик игры (`Script::LoadObject`) считает унаследованные поля по записям родителей,
    прочитанным до класса, а статические ячейки потом заполняет по всей цепочке: класс выше своего родителя в
    исходнике — переполнение кучи при загрузке объекта игрой, поэтому `compile` такое не собирает.

  Все объекты всех версий TC и AP проходят без ошибок.
- `x3kc methoddiff old.obj new.obj` — методы, код которых изменился (сдвиги не считаются).
- `x3kc savecheck src.kc base.obj` — какие адреса возврата сейвов ломает правка и почему (после адреса другой
  вызов или у метода изменился размер кадра). Считаются только вызовы, в которых задача может ждать (см.
  [kc.md](kc.md#моды-и-сейвы-x3kc-compile---base)): изменение кадра в методе, который никогда не ждёт, не мешает.
- `x3kc bugscan obj [--names auto] -o out.jsonl` — поиск типичных шаблонов ошибок (секция `switch`
  проваливается в следующую, результат геттера выброшен, `!x & n`, сравнение с размером на единицу мимо,
  скопированный геттер …): кандидаты для ручной проверки, а не находки.

## Эмулятор
`x3kc/kcvm.py` исполняет байткод так же, как `Script::Interpret` игры:
- все опкоды, кадры, вызовы (вызов по имени дополняет недостающие аргументы нулями; нет объекта или метода —
  результат 0), `fork` (первым работает потомок), задачи с ожиданием на виртуальных часах, бюджет инструкций
  (превышение бросает `Hang`: в игре такой цикл вешает кадр, у планировщика нет кванта времени);
- правила ячеек как в exe: пустая ячейка истинна; отсутствующий ключ таблицы и чтение за границей массива дают
  int 0; запись за границу массива ничего не делает; `<` / `>` не-чисел ложны (значит, `<=` / `>=` истинны);
  строки сравниваются по содержимому, контейнеры — по идентичности; `int + string` склеивает;
- таблицы скриптов устроены как в exe (4 корзины, рост вдвое, тот же перенос и порядок обхода): от этого
  зависит, какой объект скрипт найдёт первым;
- `INT_MIN / -1` и `INT_MIN % -1` бросают `VMError`: игра здесь падает (исключение целочисленного деления).

`x3kc/kcnatives.py` реализует 117 нативов SE_ / TI_ (строки, массивы, таблицы, математика, текстовые страницы,
таймеры, вычислитель выражений MSCI) по их коду в exe; поведение описано в
[natives/spec_0.jsonl](../natives/spec_0.jsonl), [spec_1](../natives/spec_1.jsonl),
[spec_2](../natives/spec_2.jsonl), включая ловушки (`SE_ToInt` от int даёт 0, `%s` от не-строки печатает
`<invalid>`, переполнение в `SE_DivFix` роняет игру …). Где exe упал бы, эмулятор бросает `VMError`. Нативы
движка (SA_, X2_, INS_, звук, 3D) отвечают 0 и записываются в журнал; тест подставляет нужные
(`vm.natives[имя] = fn`), а методы KC тоже можно подменить (`vm.overrides[имя] = fn`), чтобы отрезать мир.

```python
from x3kc import kcobj, kcvm, kcmsci
vm = kcvm.VM(kcobj.load('x3story.obj'))
vm.load_names('auto:x3story')            # имена полей для vm.get / vm.set
hq = vm.new(2046)                         # экземпляр класса 2046
vm.set(hq, 'recycleQueue', kcvm.KArray([]))
t = vm.call(hq, 'Recycle')                # исполняется, пока задача не ждёт, не вернёт или не упадёт
vm.run(60000)                             # продвинуть виртуальные часы на 60 с
```

**MSCI.** `x3kc/kcmsci.py` исполняет MSCI-скрипт настоящим интерпретатором игры: текст → сборщик
`x3kc msci asm` → codearray → `ScriptObject::__runScript` из объекта.

```python
m = kcmsci.Msci(vm, db)                   # db = msci_db.json из x3kc msci-setup
r = m.run_text(['$a = 5', '$b = $a * 3 + 1', 'return $b'])
r.type, r.value                           # 4, 16
```

**Сейвы.** `vm.migrate(new_obj)` «сохраняет» посреди ожидания и загружает в другую сборку через её запись PTCH,
как `Script::LoadVmState`: pc каждой задачи и каждый адрес возврата на её стеке переносятся, и задачи продолжают
работу на новом коде.

**Прогон всего.** `x3kc smoke old.obj new.obj` вызывает **все** методы обеих сборок с нулевыми аргументами и
сравнивает исход (вернул, ждёт, упал, завис). Различия вне изменённых методов стоит посмотреть.

**Цена MSCI.** `x3kc msci cost x3story.obj msci_db.json [строка …]` измеряет, сколько инструкций KC стоит строка
MSCI (через интерпретатор игры на эмуляторе, за вычетом пустого цикла) и какие нативы она зовёт;
`x3kc msci usage msci_db.json scripts/` считает, какие команды используют скрипты, в том числе с весом по глубине
циклов. Строка с выражением (`$c = $a + $b * 2`) стоит около 40 инструкций на токен, простая команда — 70–120.

## Что покрывают тесты
`python -m unittest discover tests`; с `X3_GAME` — ещё и тесты на объектах игры.

| Файл | Что |
|---|---|
| `test_vm.py` | язык на эмуляторе: арифметика, строки, контейнеры, циклы, `switch`, объекты, объекты классов, `fork`, таймеры, зависание |
| `test_fuzz_compiler.py` | ~900 случайных выражений и программ: `compile` + эмулятор против эталона на Python |
| `test_verify.py` | верификатор находит 8 видов порчи байткода |
| `test_b19.py` | старый сейв со сборкой `--base` переносит объекты как игра: новые поля на уровне с сохранёнными полями получают начальное значение, ниже последнего такого уровня остаются null (ошибка игры B19, компилятор предупреждает); объект удалённого класса ломает загрузку |
| `test_savesites.py` | адреса возврата сейвов — только вызовы, в которых задача может ждать (сама или через вызванный метод) |
| `test_emulator_game.py` | все объекты игры проходят верификатор; MSCI-скрипты через интерпретатор игры; мод добавляет команду MSCI (сборка с `--base`, верификатор, сейвы переносятся, команда работает, стоковый объект на ней не падает и не виснет); задача, сохранённая посреди ожидания на стоковом объекте, доходит до конца на сборке с модом |

## Чего эмулятор не знает
Мир движка (полёт, бой в 3D, столкновения) — всё, что за нативами SA_ / X2_; тайминги кадров (ожидание будит на
следующем «кадре» сразу); малую случайную добавку TI к ожиданиям (`vm.jitter`). Проверка в игре остаётся
последней ступенью, но ошибки логики, падения VM, зависания и поломку сейвов ловят до неё.
